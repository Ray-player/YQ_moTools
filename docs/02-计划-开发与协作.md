## 1. 迭代路线（v4 · 敏捷，2026-10-20 用户拍板）

> **变更原因**：原 P0→P6 瀑布式计划以「虚拟测试先行」为前提，实践中出现「反复跑 CLI / 单测，却拿不到用户可运行的产物」的偏差。
> **用户决策**：改为敏捷迭代 —— **先交付可运行 exe → 用户实机跑 → 按反馈迭代**；不以虚拟测试堆砌作为阶段门禁。

### 1.1 迭代原则（铁律）

1. **每个迭代必须产出可双击运行的 exe**（`dist/YQRec/YQRec.exe`）。只有单测通过 = 没交付。
2. 每个迭代只做**一个用户可感知的能力**，范围宁小勿大；做不完就砍，不延期。
3. **验收 = 用户实机用起来 + 反馈清单**；单测/ruff 只作回归护栏，不作阶段门禁。
4. 不做无用户价值的虚拟测试堆砌。单测只保护已交付的纯逻辑（格式解析、事件装配、坐标换算、状态机）。
5. 捕获后端与判定参数「能用即可」，具体阈值在实机反馈里调，不在空环境里反复论证。
6. 每个迭代结束必须能回答：**用户这次比上次多能做什么？**

#### 1.5.4 已知限制与技术债

| 项 | 现状 | 影响 |
|---|---|---|
| `ykq` / `yy` 的和弦区检不出 | 和弦 7 键是蓝/紫盘，不在"白盘∪棕盘"掩膜里 | 这两个乐器目前只对主区有效，需独立色域 |
| 4 个乐器的 `unpressed_ref/pressed_ref` 仍是占位 | 判别方向靠权重兜底 | 改用 `chroma` 判据前必须回填 |
| 采样半径对结果敏感 | 0.80R 最优，降到 0.40R 直接漏报 | 用户改半径后必须重学基线（界面有提示） |
| ~~UI 信息层级扁平~~ / ~~无浅色主题~~ | **M3a 已解决**：四档按钮 + 主操作迁移；日/夜双主题令牌化 | 见 §1.5.6 |
| 谱面编辑器（语法高亮 / 行号 / 错误下划线） | 仅可编辑纯文本 | M3d 功能范围，与视觉层无关 |

#### 1.5.6 视觉层现状（M3a · 2026-10-21）

| 维度 | M2q.9（重构前） | M3a（现在） |
|---|---|---|
| 配色来源 | `_apply_theme()` 里 27 行硬编码 `#hex` | **`theme.py` 令牌表**（暗/亮各 30+ 项）+ `qss.py` 单模板；QSS 与绘制代码里不再出现色值 |

## 9. 验收指标与质量门

### 9.1 指标

| 类别 | 指标 |
|---|---|
| 识别 | 单音 F1 ≥0.98；和弦 ≥0.95；onset MAE ≤20ms（p95 ≤40ms） |
| **视频源（浏览器）识别** | **F1 ≥0.90**（与源谱比对）；受保护内容能明确报"无法识别"而非静默出错 |
| 捕获 | ≥55fps、丢帧 <2%、后端自动降级可恢复；屏幕区域与窗口两模式均可用 |
| 16:9 | 720p/1080p/1440p 共用一套标定，检出率差异 <5% |
| 数据链路 | 单帧处理 p95 <8ms；**零编码零落盘**；L1 <1MB/3min；30min 无磁盘突增 |
| 播放 | 与事件表理论时间偏差 p95 ≤15ms；0.5–2.0x 不错位；循环/定位正确 |
| 编辑器 | 3000 字符无卡顿；错误定位到行；高亮跟随 |
| 导出 tick | 23 首已知谱 解析→序列化→再解析 **文本一致**；现有 tick 工具可正常播放 |
| 导出 BGI | `bgi_sim.js` 事件序列与源 Score 一致（onset 误差 ≤1ms、键序一致）；`manifest.json` 结构合法 |
| 稳定性 | 连续录制 30 分钟不崩、内存增长 <50MB |

### 9.2 迭代出口门（v4 敏捷，替代原「每里程碑全绿」）


判定：以上三条 + **用户实机跑 ≥1 次并给出反馈清单**。有反馈即迭代有效；不要求零缺陷、不要求覆盖率、不要求 P0 数据齐全。

> 原则：**能跑的 exe 优先于漂亮的指标**。指标（§9.1）保留为长期质量目标，随迭代达成，不再作为进入下一阶段的前提。

## 10. 沟通协议

- **每完成一个任务**，向 Lead 发**三行报告**：
  ```
  ① 做了什么：<一句话>
  ② 证据：<测试命令 + 结果摘要 / bench 数字>
  ③ 风险/待办：<阻塞点 或 下一步建议>
  ```
- **阻塞立即报**：不自行扩大范围、不改契约、不改别人目录。
- **禁止**：伪造测试结果、删除他人测试、`git commit`（见 §11）、引入未批准依赖、修改 `assets/**`。
- **Lead 每轮**：`team_task_list` → 派活（`send_message`）→ `wait_agent` → 评审 → 集成 → 下一批。

## 11. 版本管理（共享文件系统约定）

- 单仓库、单工作树（成员共享文件系统，**不做多分支**）；
- **只有 Lead 执行 `git commit` / `git tag`**（避免 index.lock 竞争）；成员只跑 `git status/diff`（只读）；
- Lead 在里程碑提交，message 形如 `[M2] P1 引擎: capture+vision+timeline+cli`；
- 归档点：M0 契约冻结、P0 结论、P1 CLI、P3 编辑器、P4 闭环、P6 发布。

## 文档更新规则（跨 Agent 协作）

| 场景 | 谁改 | 改哪份 | 要求 |
|---|---|---|---|
| 产品/架构决策变更 | Lead | **01** | 附决策记录（日期 + 原因 + 影响范围） |
| 接口契约变更 | 契约 owner + Lead 批准 | 01 §6 相关节 + `docs/CONTRACTS.md` | 契约升版本号并广播 |
| 里程碑/排期/人员/任务调整 | Lead | **02** | 同步任务板；写作用域变更须先广播 |
| 任务级进度 | 任何人 | **写入任务板**（team_task_*） | **不要把进度写进文档**，文档只放稳定信息 |
| 技术结论（如 P0 数据） | 该实验 owner | 02 §7 记录表 + 01 §3.1 判定 | 必须附命令与数字 |
| 曲谱格式（tick / BGI）语法变更 | 格式 owner | **07** + 03 §13 | `07` 是给 Agent/外部工具的速查，改了要同步实测表与反例 |

> 原则：**文档 = 稳定契约与知识；任务板 = 动态状态**。两者不混。
