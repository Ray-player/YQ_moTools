## 0. 一句话

**把剩下 4 个乐器（镜花之琴 / 老旧的诗琴 / 悠可琴 / 余音）从「占位参数」变成「实机能认」，同时把已登记的谐律键琴的延音真正录进谱面。核心链路（采集 / 采样 / 判按 / 装配 / UI）一行不动，改动集中在「配置 + 两处文本编解码 + 一处告警口径」。**

| 项 | 结论 |
|---|---|
| 改动量预估 | 产品代码 **≈150 行**（无新增模块，无架构变更），测试 ≈25 条 |
| 需要动核心的地方 | 只有一处：`PressDetector` 加**可选的抬起去抖**（默认 1 帧 = 现状），其余是"配置 + 文本编解码" |
| 最大风险 | **延音的视觉保持性未知**（谐律键琴按住时键帽是否持续高亮）→ M4a 必须先做一次门禁实验，两条路都已备好 |
| 已可确认的好消息 | 参考图实测：**单一权重 + 逐键基线**就能同时兼容悠可琴/余音的"第一行与另外两行配色不同"，不需要 per-area 代码改动 |
| 需要纠正的既有认知 | ① `fwzs` 的 B 通道权重偏高（0.205 → 应 0.08）；② 填了 `refs` 后悠可琴会**每次学基线都误报"基线可疑"**（双区色差被当成按下），必须先修告警口径 |

### 3.3 建议权重与判据余量

`score = Σ w_c·max(0, Δ_c − 8) / Σ w_c`（`tolerance=8`），**score 取该乐器"最差的那个按下键"**（不是平均），余量 = `score / Δ`。

> 工具打印的 `score` 是"平均 Δ"口径（略高于下表），下表已换算成最差键 —— 保守值才是判据余量的正确度量。

| 乐器 | 建议 `weights` | 主区 score（最差键） | 和弦行 score | 建议 Δ | 最小余量 | 与现值比 |
|---|---|---|---|---|---|---|
| `fwzs` | **0.84 / 0.09 / 0.07** | 83 | — | 20 | 4.1× | B 权重从 0.205 降到 0.08（现值的 B 跌幅只有 10，旧权重在稀释信号） |
| `xlyq` | 0.19 / 0.31 / 0.50 | 51 | — | 20 | 2.6× | 基本一致（0.193/0.307/0.5） |
| `jhzq` | 0.19 / 0.30 / 0.51 | 45 | — | 20 | 2.3× | 微调 |
| `ljdsq` | 0.39 / 0.17 / 0.44 | 45（降号键 ≈39） | — | 20 | 2.2×（降号键 2.0×） | 基本一致 |
| `ykq` | 0.43 / 0.34 / 0.23 | 132 | **38** | **15** | 2.5× | 和弦行余量只有主区的 29% → Δ 必须 ≤15 |
| `yy` | 0.45 / 0.43 / 0.12 | 63 | **56** | 20 | 2.8× | — |

**调参规则（写进 03）**：

```
Δ = min( round(该乐器最小 score / 2.5), 20 )   # 向上取不超过 20
```

理由：未按下侧的实测干扰只有 2–6 灰阶（扣掉方标影响后更小），Δ=15 仍比干扰高 2.5 倍以上；而按下侧必须留 ≥2.5 倍余量，否则实机动画/压缩噪声会吃掉它。**只降不升**（升 Δ 是"漏音"投诉的最常见原因）。

## 4. 难点 ①：谐律键琴的延音

### 4.1 问题拆解（不要一上来就写算法）

| # | 子问题 | 现状 |
|---|---|---|
| P1 | **视觉是否保持**：按住时键帽是否一直是"按下色" | 未知（参考图是静帧）。若按下瞬间亮起后回弹 → 现有判据会在回弹那一帧判"抬起"，延音被截到 150–300ms |
| P2 | **文本层丢失**：`tick_text()` 不写 sustain | 确定存在（§1.2） |
| P3 | **抬起抖动**：`PressDetector` 单帧不满足即抬（`if not keep`） | 一次闪帧就把一个长音切成两个音 |
| P4 | **残留拖尾**：抬指后键帽有退色动画 | 会把延音拉长 100–300ms |
| P5 | **游戏自身限制**：某些乐器延音有上限（自动停） | 不需要特殊处理 —— 识别到"抬起"就照实记，这正是我们要的结果 |
| P6 | **和弦内不同键时长不同** | 现有 `assemble()` 取 `max(hold)`，即以最长者为整和弦延音；对 BGI（每个键独立 keyUp）够用，谱面语义要写清楚 |

### 4.2 决策树（M4a 走完 G-S1 后按结论分叉）

```
G-S1：按住 2s 的"按下态"是否全程可见？
│
├─ 是（score 在按住期间 ≥Δ 的帧占比 ≥95%）
│    └─ 路径 A（最可能）：只补文本层 —— P2 + P3 + P6
│
├─ 否，但"回弹后仍有一圈持续光晕/外环高亮"
│    └─ 路径 B：加"延音证据通道"（外环 1.02R~1.20R 的亮度），与主判据 OR
│
└─ 否，且没有任何持续视觉线索
     └─ 路径 C：不做自动延音。谱面输出 [0]，UI 提示"本乐器延音需手工标注"，
                并提供"按下一同键间隔推断"开关（默认关，sustain = min(gap_next, 上限)）
```

### 4.3 G-S1 门禁实验（M4a 必做，1 次实机 5 分钟）

**工具**：`tools/sustain_probe.py`（新增，独立脚本，零产品风险）

```bash
# 前置：游戏里选好谐律键琴 → 框选 → 学习基线（全部松开）
.venv/Scripts/python.exe tools/sustain_probe.py --seconds 10 --dump out/sustain.npz
# 脚本读 %APPDATA%\YQ_moTools\profiles\default.json 的 keygrid + baseline + thresholds，
# 抓 N 秒，逐帧算每个键的 weighted score，落盘 (ts, score[K]) 并打印摘要
```

**动作脚本**：A 按住 2s → 松 1s，重复 3 次；再按住 400ms 松 500ms，重复 3 次。

**判读标准**（三项全过 = 路径 A）：

| 指标 | 通过标准 | 不通过的含义 |
|---|---|---|
| 按住段内 `score ≥ Δ` 的帧占比 | **≥ 95%** | 中途回弹 → 路径 B |
| 抬起后 score 归零所需帧数 | **≤ 5 帧（≈80ms）** | 拖尾长 → 需要 `sustain_tail_trim_ms` |
| 按住段内 score 的中位数 | **≥ 1.5×Δ** | 按住时颜色会"软化"（更浅），可能要在按住态单独降 Δ |

**输出记录**：把 `out/sustain.npz` 的摘要贴进本文 §4.8 的结论表，后续接手的人不用重测。

### 4.4 路径 A（推荐）：把 hold 写进谱面 —— **已实现（2026-10-22）**

改动只有三处，全部是"编解码 + 去抖"，不碰采样与判据。

#### 4.4.1 谱面语法：`A[500]`

在现有毫秒间隔方言（`A1000F` = 按 A，隔 1000ms 再按 F）上增加**和弦级延音后缀**：

```
<CHORD>[<ms>] <gap_ms> <CHORD>[<ms>] <gap_ms> ...
```

| 规则 | 说明 |
|---|---|
| 位置 | `[` 必须紧跟和弦字母；`]` 后才是间隔数字 |
| 阈值 | `sustain_ms < 50` **不写**（与 01 §7.1 的 `.sustain_ms >= 50 才输出` 对齐） |
| 取整 | `round()` 到毫秒 |
| 和弦内不一致 | 写 `max(hold)`（沿用 `assemble()` 现有语义）。本格式**没有 per-key 延音**，这是格式约束，UI 的 tooltip 要写明"和弦延音取最长键" |
| 例 | `A[800]1000F` = A 按住 800ms，A 的 onset 之后 1000ms 按 F |

**为什么不用 `A.500`**（`formats/tick.py` 的老写法）：`.` 后面直接接间隔数字会变成 `A.5001000F` 这种"数字连成一串"的文本，人读不了、正则也难断。`[...]` 有明确边界，且旧版解析器会忽略方括号、把里面的数字当成一个独立的 gap 片段 —— 当延音后**还有**间隔数字时（`A[800]1000F`），旧版读到的时序与新版一致，只丢延音；但延音后**紧跟**下一个和弦时（gap=0，`A[800]F`），旧版会把 800 当成间隔 → 时序错位。所以仍要靠版本号声明，不能指望"静默降级"。

> 兼容声明：`scorefile` 的 JSON `version` 由 4 升到 **5**，新增 `tick.sustain: true` 标志。用旧版 exe 打开 v5 文件时延音会丢（不报错），使用说明里写明"延音谱面请用 M4c 之后的版本打开"。

#### 4.4.2 代码改动（3 个函数 + 1 个字段）

| 文件 | 函数 | 改动 |
|---|---|---|
| `src/yqrec/recording.py` | `tick_text()` | 每个 note 的后缀：`"".join(keys)` + (`f"[{round(sustain_ms)}]"` if `sustain_ms >= 50`) |
| 同上 | `scan_tick_tokens()` | 扫完字母后，若 `text[i] == '['` → 读到 `]` 的整数为 sustain（非法则 0 + 忽略）；`TickToken` 新增 `sustain_ms: float = 0.0` |

#### 4.4.3 抬起去抖（P3，唯一碰"核心"的地方）

`PressDetector` 现在是"单帧不 keep 即抬"。加**可选的连续帧确认**，默认 1 = 行为完全不变：

```python
# DetectorConfig
release_confirm_frames: int = 1     # 1 = 现状；2~3 = 抬起去抖（延音乐器建议 2）
```

状态机（与按下侧 `pending_since` 对称）：

```python
else:  # 已按下
    if not keep:
        if st.up_pending_since is None:
            st.up_pending_since = ts          # 记第一个"不满足"的帧
        st.up_seen += 1
        if st.up_seen >= release_confirm_frames:
            st.down = False; st.up_pending_since = None; st.last_up_ts = ts
            out.append(PressEvent(key=key, down=False, ts=<up_pending_since>))  # ★ 时间戳取首帧
    else:
        st.up_pending_since = None; st.up_seen = 0
```

> ★ **抬起时间戳取"第一个不满足的帧"而不是确认帧**：既去掉抖动，又不把延音整体拉长 1–2 帧。这一点和按下侧 (`st.down_ts = st.pending_since`) 是同一个设计原则，测试要锁住（`test_release_debounce_keeps_timestamp`）。

参数落点：`instruments.json` → 乐器 `detection.release_confirm_frames`（int 1–5，默认 1）。**只有 `sustain=true` 的乐器建议 2**，其余保持 1（短音去抖会吃掉 16–33ms 的时序精度）。

### 4.9 追问复核（2026-10-22）：叠音与 yuanqin 延音

#### 4.9.1 yuanqin 到底支持不支持延音？

**支持，但只支持"单声部延音"。** `type: "yuanqin"` 的每个 token 是
「按下 → 按够时值 → 抬起」，时值就是 keyUp 时刻（`parse_yuanqin` 读回来就是
`sustain_ms`），所以单纯的"一个音按住多久"表达得了；但 token 是**顺序播放**的，
一个键还按着、另一个键就响 —— 这种叠音表达不了（B 站原琴脚本也是这个模型）。

实测（`bpm=300`，时值表 1/1.5/2/3/4… 倍）：

| 谱面文本 | yuanqin 输出 | 读回 | 结论 |
|---|---|---|---|
| `A[800]2000D` | `A[1]｜@[1-*]｜D[8]` | (0,800)、(2000,100) | ✅ 完整保留（音之间有空隙） |
| `AD[800]1000FG` | `(AD)[1]｜@[4](FG)[8]` | (0,800)、(1000,100) | ✅ 和弦能表达 |
| `A[750]` | `A[1]` | (0,800) | ⚠️ 量化 +50ms（旧实现向下取整是 −150ms） |
| `A[1200]304DF[992]` | `A[4-*](DF)[1]` | (0,300)、(300,800) | ❌ 叠音被压平：A 的 1200 → 300 |

因此这一轮补了两件事（契约 v1.36）：

1. **就近取档**：`_yq_nearest_ms()` 在"不超过下一个音起点"的前提下挑最接近的时值，
   长音量化误差从 −20% 降到 ±10%（750 → 800 而不是 600）；
2. **如实报损**：`yuanqin_sustain_loss(score, spec)` 统计叠音截断 + 量化损失，
   保存 `BGI · yuanqin` 后状态栏出 warn：「N 处延音被截短（最长 Xms），要完整延音请改存 BGI · midi」。

> 结论（给用户的话）：**谐律键琴要连延音一起导进 BetterGI，请用 `BGI · midi`** ——
> 1 tick = 1ms、逐键 D/U 事件，支持"低音按住、旋律在上方走"，延音与叠音都不丢；
> `yuanqin` 只适合给五线谱制谱器做单声部草图。

#### 4.9.2 按住一个键的同时按其他键，能认对吗？

**能。** 判按是**逐键独立的状态机**（21 个 `_KeyState` 各自施密特触发），按住 A 不会
产生任何事件，也不影响 D/F 的判定；装配阶段 `_pair_notes` 按 key 配对、`_group_chords`
按 onset 分组，所以"先按下的长音"天然自成一个更早的和弦。

实测时间线（60fps 合成帧，谐律键琴阈值 300ms）：

```
0ms 按 A → 304ms 按 D+F → 1200ms 松 A → 1296ms 松 D+F
tick : A[1200]304DF[992]
BGI  : DA0 | DDF304 | UA896(=1200ms) | UDF96(=1296ms)
```

三个要点都有回归用例（`tests/test_sustain_recording.py`）：

| 用例 | 保证什么 |
|---|---|
| `test_hold_while_pressing_other_keys` | 整链路：延音不被后续按键打断，onset/gap 正确 |
| `test_bgi_midi_keeps_overlapping_holds` | `midi` 里 A 的抬起仍在 1200ms（不被 D/F 顶掉） |
| `test_sustain_does_not_affect_onsets` | 叠音时 `rest = onset_{i+1} − onset_i` 语义不变 |

**残留风险（需实机确认，代码侧无法测）**：相邻键按下的**光效/涟漪**可能溢出到本键的
采样环上。weighted 判据只累加"变暗"，邻键高亮不会把本键判成按下（方向相反），
但如果动画让本键**变暗**（阴影/压暗），就会出现"连带按下"。若实机出现，
把 §4.5 的采样环半径收窄（0.80R → 0.72R）或给邻键加角度屏蔽。

### 5.2 为什么"底色不同"其实不用处理

判据是**相对自己基线的跌幅**，不是绝对色：

```
score = Σ w_c · max(0, (base_c − cur_c) − 8) / Σ w_c
```

- `base_c` 来自**逐键基线**（`PressDetector(baseline=(K,3))`，v1.20 起默认）；和弦行 7 个键的 base 是蓝盘值，主区 14 个键是米白值 —— **底色差异在构造时就被消掉了**；
- 若某天退化成区域均值基线，和弦行会立刻"常按不亮"，这也是 03 §16.3 那条"为什么必须逐键"的延伸证据。

### 5.3 为什么"单一权重"仍然够用（这是本节的核心结论）

两区的最优权重方向：

| 乐器 | 主区最优点 | 和弦行最优点 | 用主区权重的和弦行 score | 用和弦行权重的和弦行 score |
|---|---|---|---|---|
| `ykq` | (0.43, 0.34, 0.23) | (0.25, 0.31, 0.44) | **38** | 45 |
| `yy` | (0.45, 0.43, 0.12) | (0.30, 0.33, 0.37) | **56** | 58 |

- `yy`：差值 <4%（因为和弦行 7 键也是"整体变暗"），**完全不需要分区权重**；
- `ykq`：差值 16%，但 38 仍 ≥ 2.5×Δ(15) —— 用主区权重（14 键最优）是正确取舍；
- 两区最优方向的**几何平均几乎就是等权**（`sqrt(0.43×0.25)≈0.33`），说明这两个乐器的按下反馈本质是"整体变暗、无色偏" → **禁用 `chroma`**（色偏判据假设两区同向，这里会打架）。

### 5.4 结论与参数

| 乐器 | Δ | weights | 备注 |
|---|---|---|---|
| `ykq` | **15** | 0.43 / 0.34 / 0.23 | 和弦行余量 2.5×（38/15）；实机若误报再回 18 |
| `yy` | 20 | 0.45 / 0.43 / 0.12 | 和弦行余量 2.8× |

### 5.5 必须先修的副作用：`_suspicious_baseline_keys()` 的误报

```python
# 现状（ui/main_window.py:1753）：全 21 键一把算，跨越了两种底色
values = baseline[:, base_to] - baseline[:, base_from]
median = float(np.median(values))

```

| 乐器 | `chroma_axis` | 和弦行 `B−R` | 主区 `B−R` | 结果 |
|---|---|---|---|---|
| `ykq`（填 refs 后） | (R→B) | **+117** | −15 | 中位数 −15，7 个键全被判离群 → **每次学基线都报警** |
| `yy`（refs=null 时） | (R→G) | 4 | 1 | 恰好不报；**填了 refs 后会变成 (R→B) 并开始误报** |

**修法（3 行）**：把离群检测改成**按 area 分组**各算各的中位数 —— 同一 area 内的键共用一套底色，这正是这个检查的原始假设。

```python
def _suspicious_baseline_keys(self) -> list[str]:
    ...
    key_index = {k: i for i, k in enumerate(self._spec.key_order)}
    out: list[str] = []
    for area in self._spec.areas:                 # ★ 按区
        idx = [key_index[k] for k in area.keys if k in key_index]
        vals = self._baseline[idx, base_to] - self._baseline[idx, base_from]
        med = float(np.median(vals))
        out += [self._spec.key_order[i] for i, v in zip(idx, vals, strict=False)
                if abs(float(v) - med) > BASELINE_OUTLIER_SHIFT]
    return out
```

验收：`ykq`/`yy` 学完基线**不报警**；故意按住 2 个键学基线时仍然报警（把回归用例 `test_baseline_outlier_*` 扩成双区）。

## 6. 难点 ③：老旧的诗琴「b」符号

### 6.1 它到底在哪儿、影响多大（实测）

b（降号）是绿色的字形，画在**音符图标左侧**，部分压在盘面上、部分溢出盘外（见 `out/crop_ljdsq_b.png`）。带 b 的键（8 个）：`W E Y U S J C N`。

8 个采样点里，**正左方（180°）那个点**会落在字形上：

| 键 | 是否带 b | 8 点中最暗点的角度 | 该点 RGB | 8 点均值 RGB | 相对同排中位数 |
|---|---|---|---|---|---|
| W | ✓ | 180° | (208,218,188) | (242,239,223) | −1 / 0 / −1 |
| E | ✓ | 180° | (194,206,173) | (241,238,221) | +1 / +1 / 0 |
| U | ✓ | 180° | (158,185,134) | (230,230,210) | **+11 / +8 / +12** |
| J | ✓ | 180° | (159,186,136) | (230,230,210) | **+15 / +10 / +17** |
| C | ✓ | 180° | (196,206,175) | (241,238,221) | +7 / +5 / +8 |
| Y | ✓ | **90°（下方）** | (213,209,183) | (242,238,222) | 0 / 0 / 0 |
| S | ✓ | 90° | (226,221,197) | (248,243,229) | −2 / −2 / −3 |
| N | ✓ | 90° | (215,210,183) | (247,242,227) | +2 / +2 / +2 |
| 非 b 键（A/D/G/H/Z/X/V/B） | ✗ | 均为 90° | — | (245–250,241–245,225–231) | ±4 |

三个结论：

1. **b 的污染不是"整排一致"，是"每键不同"**：只有 `U/J/C` 的 180° 点真的踩在字形上（8 点均值低 8–17 灰阶），`W/E/Y/S/N` 的字形主要落在盘外 → 影响 <3 灰阶。
2. **另有一个所有键共有、与 b 无关的现象**：8 点里"正下方（90°）"那个点落在**圆盘下方的键名文字 / 白色方标**上，偏离 12–40 灰阶。按用户说明，实机流程没有那个方标 → **不要为它改算法**（这也是 B2 的由来）。
3. **污染只稀释 1/8 的信号**：按下时盘面变绿、字形不变 → `Δ_带b ≈ 7/8 × Δ_普通`。`ljdsq` 普通键 score 45 → 带 b 键 ≈ **39**，Δ=20 时余量仍有 **2.0×**。

### 6.2 因此：**M4 不为 b 符号改采样代码**

| 措施 | 是否做 | 说明 |
|---|---|---|
| 逐键基线 | 已具备 | 把 b 键的"天生偏暗"完全吸收（这也是为什么只有 3 个键看起来"偏暗"却不会误判） |
| Δ 不升过 20 | 是 | 带 b 键余量 1.9× 是全局最小的，Δ=25 就只剩 1.5× |
| 采样半径 ≤ 0.85R | 是（写进使用说明） | 0.90R 时左点会踩到盘外背景（b 溢出部分），信噪比骤降 |
| 角度避让 | **仅当实机余量不足**（见 6.3） | 需要加配置字段，属于 M4c 之后的可选补丁 |
| 方块模式 | 否 | 0.55R 方块左边界在 −0.55R，字形在 −0.6R~−1.0R 之间，**反而更容易踩到字形边缘**，不作推荐 |

### 6.3 若实机验证不通过：角度避让（备选设计）

**症状**：带 b 键在实机上无法点亮，或要点很重才亮（`score < 2×Δ`）。

**方案**：把环形采样点数从 8 降到 6，并旋转 30° —— 采样角变成 `30/90/150/210/270/330`，最近的两个点距 180° 有 30°，完全避开字形（字形张角实测约 ±22°）。

```jsonc
// 实现形态：乐器级 sampling 覆盖（缺省回落全局 sampling 段）
"sampling_override": {"ring_points": 6, "ring_start_deg": 30}
```

| 改动点 | 内容 | 行数 |
|---|---|---|
| `types.SamplingSpec` | 加 `ring_start_deg: float = -90.0` | 2 |
| `vision/pointsampler.ring_base_points()` | 起点角用参数而非常量 `-math.pi/2` | 2 |
| `instruments.InstrumentSpec` | 加 `sampling_override: dict \| None`，解析时 merge | ~10 |
| `ui/capture_worker` + `ui/preview` | 采样器/红点用 merge 后的几何 | ~10 |

代价：改了采样几何 → **该乐器必须重学基线**（用户本来也要学，可接受）。收益：带 b 键 score 回升到 ≈45（与其他键齐平）。

### 6.4 验收

| 用例 | 标准 |
|---|---|
| 逐键点亮 | `ljdsq` 21 键逐个按，全部点亮（含 8 个 b 键） |
| 余量 | 带 b 键 `score / Δ ≥ 1.8`（用 `keys_panel` 的 Δ 数值读数记录） |
| 静置误报 | 松开 30s，0 次误亮 |
| 参考图回归 | `tools/reftex_colors.py` 对 `ref_老旧的诗琴.png` 输出的按下键集合 = {Q,F,M} |

## 8. 给接手者的三条提醒

1. **参考图只解决"颜色"，不解决"几何"**。`assets/refTex` 的 10 张图都带白色键名方标，颜色法在上面必然失败（46 轮廓 → 2 个过筛），Hough 也只出 12–19 个圆。想要 21 个圆的真实校验，必须用**实机无方标截图**。
2. **口径必须一致才有可比数字**。本文所有 Δ / 权重都是「环形 0.80R × 8 点 + patch 0.06R」口径；换方角/换点数/换半径都要重测，否则会和 03 §5.1 里那些环带均值时代的数字打架（`fwzs` 的 B 跌幅 25 ↔ 10 就是这个原因）。
3. **先修告警口径，再填 refs**（§3.4、§5.5）。顺序反了，用户第一次给悠可琴学基线就会看到"基线可疑：7 个键"，然后怀疑程序坏了。
