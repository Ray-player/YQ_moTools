## 0. 摘要

**一句话**：框一块屏幕区域 → 你在游戏里弹 → 实时判键 → 生成谱子 → 在编辑器里试听微调 → 导出 tick 谱或 BetterGI 脚本。

| 项 | 结论 |
|---|---|
| 可行性 | **高**。识别算法（Hough 定位 + 颜色阈值判键）经 23 首真实谱与完整实现验证；把"解码 mp4"换成"抓屏幕区域"是降复杂度 |
| 核心链路 | **逐帧截取 → 内存分析 → 只存 21 键 RGB 时序（不落图、不编码视频）** |
| 最大未知 | **G2：「按下 = 变暗」的真实信噪比**（已在实机端到端验证） |
| 截图方案 | MAA 式**多后端 + 自动测速 + 失败回退**；**默认目标是"任意屏幕区域"→ DXGI**，选窗口模式时 → WGC（可排除自身 HUD）；GDI/PrintWindow 兜底 |
| 一期范围 | 无延音 5 乐器（全 21 键、全有 mp3）+ 识谱 + 播放器 + 编辑器 + tick/BGI 导出 + 打包；**识别源含游戏窗口与浏览器视频** |
| 体积 | 不限；PySide6 + OpenCV + 4 捕获后端，onedir 约 250–350 MB |

## 1. 产品定义

### 1.1 功能清单

| 模块 | 一期 | 二期 |
|---|---|---|
| 屏幕捕获 | **任意屏幕区域**（游戏 / 浏览器视频 / 播放器 / 任意窗口）+ 16:9 锁定 + 配置档；窗口模式用于排除遮挡 | 自动识别视频内容区（去黑边）、被遮挡/最小化捕获 |
| 键位标定 | Hough 自动 + 手动点选兜底 + 网格吸附 | 自动乐器识别（HSV 模板打分） |
| 识谱 | 无延音 21 键（5 种乐器） | 延音乐器（谐律键琴/跃律琴）+ 14 键（晚风圆号/沃雅妮莎） |
| **播放预览** | **三类格式读取 + 采样音频播放（变速/循环/定位/当前和弦高亮）** | 14 键乐器的 MIDI 预览 |
| **编辑器** | **语法高亮 / 错误标记 / 播放同步滚动 / 撤销重做 / 另存** | 量化到 BPM 网格、区间替换、批量变换 |
| 导出 | **tick + BetterGI JS** | 风物谱 / Domiso / MIDI |
| 打包 | onedir + Inno Setup | （自动更新可选） |

### 1.2 识别源的通用性（不只是游戏）

**本工具不绑定游戏窗口**。识别管线的输入被抽象为「用户框选的一块屏幕区域」，只要这块区域里出现的是**原神乐器界面**（21 键 / 14 键的三排琴键 UI），来源可以是：

| 来源 | 典型场景 | 说明 |
|---|---|---|
| **游戏窗口**（原神 / 云原神） | 自己弹、录制自己 | 最常用；云原神不支持（串流压缩） |
| **浏览器播放的视频** | B 站 / YouTube 上的原神演奏录像 | **一等公民**；用于"没有游戏也能转谱" |
| **本地播放器 / 剪辑软件** | 本地录屏、PR 时间轴预览 | 同上 |
| **任意窗口/桌面区域** | 直播画面、远程桌面里的游戏 | 只要画面可冻结、颜色不失真 |

因此设计里有两条"目标模型"（详见 §6.1）：

- **屏幕区域（默认）**：`monitor + 屏幕矩形` → 真正任意区域，跨窗口也行；后端走 DXGI（桌面复制后裁剪）/ GDI。
- **窗口区域（可选）**：`hwnd + 客户端归一化矩形` → 用于"排除自身 HUD 遮挡"或"窗口被其他窗口盖住"的场景；后端走 WGC / PrintWindow。

**两种模式的差别只有"怎么取帧"**：之后的归一化、Hough、采样、判按、装配、导出完全相同。

**视频源特有的注意事项**（必须让用户在 UI 上看到）：

| 事项 | 影响 | 处理 |
|---|---|---|
| 视频是 YUV **4:2:0** 有损压缩 | 单键 R/B 均值可能漂移几到十几灰阶 → 阈值更脆 | 标定向导按"当前源"独立标定；G8 单独验收；必要时退到双模板匹配 |
| 播放器开了**画质增强/插帧/锐化** | 颜色被二次处理 | 提示关闭；或标定时以实际画面为准 |
| **播放速度 ≠ 1.0x** | 时间轴被拉伸/压缩，谱面时长失真 | 提示用 1.0x；导出时文档标注 |
| **DRM / 受保护内容** | 截图全黑 | 检测连续黑帧 → 明确提示"该内容受保护，无法识别" |
| 视频内有**进度条/字幕/水印** | 误判为按键 | 框选时避开；或加"顶部/底部屏蔽带" |
| 视频分辨率/黑边 | 几何偏移 | 16:9 内容区吸附（去黑边）或手动精框 |

## 3. 可行性

### 3.1 关键前提与判定标准（G1–G8）

> 这里是**判定标准**（"怎样才算成立"）。对应的实验步骤、负责人、记录表见 02 §7。

| # | 前提 | 通过标准 | 不通过怎么办 |
|---|---|---|---|
| **G1** | 16:9 归一化后 Hough 能检出 21 圆 | 1080p/1440p 默认画质 **≥90%** 帧精确检出 | 降级为"手动点 21 点 + 网格吸附"主路径 |
| **G2** | **"按下=变暗"信噪比足够** | 通道均值差 **≥25 灰阶**、`Δ/std ≥ 2.5` | 改"按下/抬起双模板匹配"分类 |
| **G3** | 捕获后端可用且够快 | WGC/DD 至少一种稳定 **≥55 fps** | 调后端策略；要求无边框窗口 |
| **G4** | 时序精度足够 | onset 误差 **p95 ≤ 40ms**（以节拍器为参考） | 提 FPS / 用捕获时间戳插值 |
| **G5** | 端到端可用 | 23 首 DefaultSheet 播放→录→识别 **F1 ≥ 0.95** | 定位漏检/误检，调阈值与去抖 |
| **G6** | 自身 HUD 不污染采样（**仅屏幕区域模式**） | 叠加 HUD 时采样漂移 **< 3 灰阶** | 窗口模式（WGC 排除他窗）；HUD 自动避开区域；或录制时隐藏 HUD |
| **G7** | 数据链路成本可控 | 「帧→分析→丢」单帧 p95 **<8ms**、**零落盘** | 降采样步长 / 只采 ROI |
| **G8** | **视频源（浏览器播放）可用** | 1080p 原神演奏视频：标定能通过，且识别 **F1 ≥ 0.90**（低于本地的 0.98 属预期） | 双模板匹配兜底；提示关闭画质增强；文档标注"视频源精度较低" |

> **G2 是最大未知**；**G6 决定屏幕区域模式下的 HUD 策略**；**G7 钉死"不落盘"**；**G8 决定"浏览器视频"能不能作为一等公民**。

### 3.2 为什么可行

琴键定位、取色、判按、格式语法均已定稿并被 23 首真实谱验证（Hough 找圆 + 网格校正 + 颜色阈值判按的路线）；播放器逻辑（TickScore→Chord→定时→发声）可直接用 Python 实现；mp3 采样现成；BGI JS 与 tick 语法均从官方文档确认。

### 3.3 截图方案对比与定稿（决策 6）

**BetterGI**：`Vision.WindowCapture` + `CaptureModeEnum { BitBlt, WindowsGraphicsCapture }`（[源码](https://gitee.com/oma/BetterGI/blob/async-startup-fix/Vision.WindowCapture/CaptureModeEnum.cs)）。**用户手选**，无自动测速/回退。文档明确 BitBlt 在 Win11"窗口化游戏优化"下会失效，需手动关闭。

**MAA（MaaFramework Win32）**：6 种方法枚举，**启动时测速取最快可用**（[枚举文档](https://maaxyz.github.io/MaaFramework.Binding.CSharp/api/MaaFramework.Binding.Win32ScreencapMethods.html)）：

| 方法 | 速度 | 兼容性 | 需管理员 | 后台/遮挡 |
|---|---|---|---|---|
| GDI（BitBlt） | 快 | 中 | 否 | 否 |
| FramePool（WGC） | 很快 | 中 | 否 | **是** |
| DXGI_DesktopDup | 很快 | 低 | 否 | 否 |
| DXGI_DesktopDup_Window | 很快 | 低 | 否 | 否 |
| PrintWindow | 中 | 中 | 否 | **是** |
| ScreenDC | 快 | 高 | 否 | 否 |

预置组合：前台 = `DXGI_DesktopDup_Window | ScreenDC`；后台 = `FramePool | PrintWindow`。

**定稿：以 MAA 的"多后端 + 自动基准 + 回退"为骨架；按目标类型路由后端——屏幕区域 → DXGI（唯一能抓任意子矩形的方案），窗口 → WGC（可排除自身 HUD）。**

| 维度 | BetterGI | MAA | 本方案 |
|---|---|---|---|
| 后端数 | 2 | 6 | **4**（WGC / DXGI / GDI / PrintWindow） |
| 选择 | 用户手选 | 自动测速 | **自动基准 + 运行中回退 + 可锁定** |
| 排除自身 HUD | WGC 可以 | FramePool 可以 | **窗口模式用 WGC；屏幕区域模式靠 HUD 避让/隐藏** |
| 任意子矩形（浏览器视频） | 不支持（只窗口） | DXGI 裁剪可 | **ScreenTarget → DXGI，支持任意区域** |
| 坐标 | 窗口 | 窗口 | **窗口客户端归一化坐标**（移动/缩放不失效） |

理由：本产品"框选 + 悬浮 HUD"必然自我遮挡，DXGI 拍合成后的屏幕会把 HUD 也拍进去（G6）；WGC 窗口级捕获天然排除；DXGI 保留速度备选，GDI/PrintWindow 兜底。

### 3.4 明确不做 / 已知限制

- ❌ 云原神（串流压缩 + 硬件解码，颜色判定不可靠；BGI 同样不支持）
- ❌ HDR（颜色空间不同；可检测到后提示关闭）
- ⚠️ 超快连击：有效帧率 30–60fps，**>12 音/秒会漏检**（文档与 UI 都要写明）
- ⚠️ 非 16:9：可用但几何有偏差，UI 给警告

## 4. 数据链路（核心）

### 4.1 只有一种做法

| 做法 | 本方案 |
|---|---|
| 录视频（mp4）再解码分析 | ❌ 不做，且**实现里没有视频编码代码** |
| 存每帧 PNG 落盘、事后分析 | ❌ 不做（默认） |
| **逐帧截取 → 内存立即分析 → 只留数值** | ✅ **唯一路径** |

每帧拿到 `numpy` 数组 → 算"21 个键的 ROI 均值"（21×3 字节）→ 丢弃该帧。分析链路里**没有编解码、没有磁盘写入**。

### 4.2 为什么不用视频/图片

1. **颜色会被破坏**：H.264/HEVC 是 YUV **4:2:0**，色度只有 1/4；判据恰是单键 **R/B 通道均值**。有损编解码会让均值漂几到十几灰阶、边缘出块效应 → 阈值失效。
2. **延迟与抖动**：编码排队 + 写盘周期卡顿；实时判按要求每帧 16.7ms 内完成。
3. **抢 GPU**：游戏在吃 GPU，软编拖慢游戏与捕获；WGC/DXGI 拿的是合成器现成内容，额外 GPU≈0。
4. **没必要**：唯一"重算"需求（改阈值/去抖）只要数值序列。

### 4.3 数据量

| 形态 | 体积/分钟 | 有损 | 备注 |
|---|---|---|---|
| H.264 1080p60（8–12 Mbps） | 60–90 MB | **是（4:2:0）** | 不采用 |
| PNG 序列 @60fps | 18–60 MB **/秒** | 否 | 编码 10–30ms/帧，拖垮流水线 |
| **每键 RGB 时序 `samples.npz`** | **≈0.26 MB**（3 分钟 ≈0.8 MB） | 否 | 就是分析输入，天然可重算 |

> 71 B/帧（21×3×1B + 8B 时间戳）× 60fps = 4.3 KB/s。

### 4.4 四层数据

| 层 | 内容 | 生命周期 | 默认 |
|---|---|---|---|
| **L0 捕获帧** | BGR `numpy`（区域尺寸） | **1 帧**，分析完即释放 | 常驻内存 |
| **L1 特征序列** | `samples.npz`：`ts[F] float64` + `rgb[F,K,3] uint8` | 会话级 | **必存**（≈0.8MB/3min） |
| **L2 调试快照** | 环形缓冲最近 N 帧 + 一键导出 PNG（限帧限时） | 内存滚动，按需落盘 | **关闭**（120 帧约 170MB） |
| **L3 产物** | tick `.txt` / BGI 脚本目录 / `meta.json` | 长期 | 用户触发 |

- L2 只用于"这一帧为什么判错"的人工复核；默认不占内存。
- UI 标定用的预览帧是**降采样副本**（约 480 宽、10–15fps，仅内存），不参与识别。
- 回归/评测片源必须是**无损**（PNG 序列 / FFV1 / x264 `-qp 0`）；`FileBackend` 读 mp4 只验证流程，**不用于标定阈值**。

### 4.5 线程模型

```
[后端捕获线程]  windows-capture / dxcam 内部线程
      │ 最新帧（回调或拉取）
      ▼
[分析线程]  取 ROI（按比例映射）→ 21×3 均值 → 状态机 → 追加 L1
      │  · 每帧 <5ms；不写盘、不编码
      │  · 每 500ms 推一张降采样预览帧给 UI
      │  · 每 200ms 推统计快照（fps / 已识别音数 / 当前按键）
      ▼
[UI 线程]  Qt 事件循环（只消费快照与预览帧）
[音频线程] pygame.mixer 混音线程（播放预览时）
```

单消费者（分析线程唯一读帧）、无锁、无背压；UI 永不碰捕获对象。


## 6. 关键设计

### 6.1 捕获层

```python
# 两种目标模型（决策 8）
@dataclass(frozen=True)
class ScreenTarget:                       # 默认：任意屏幕区域（跨窗口也行）
    monitor: int                          # 显示器索引（多屏）
    rect: tuple[int, int, int, int]       # 屏幕物理像素 (l, t, r, b)，16:9
    offset: tuple[int, int] = (0, 0)      # 相对显示器原点的偏移

@dataclass(frozen=True)
class WindowTarget:                       # 可选：绑定一个窗口（排除遮挡/HUD）
    hwnd: int
    client_norm: tuple[float, float, float, float]   # 客户端归一化 (u0,v0,u1,v1)

CaptureTarget = ScreenTarget | WindowTarget

class CaptureBackend(Protocol):
    def supports(self, target: CaptureTarget) -> bool: ...
    def open(self, target: CaptureTarget) -> None: ...
    def latest(self, timeout_ms=100) -> tuple[np.ndarray, float] | None: ...
    def close(self) -> None: ...
    def stats(self) -> CaptureStats: ...   # fps / dropped / last_error
```

**目标 × 后端矩阵**

| 目标 | 首选 | 备选 | 说明 |
|---|---|---|---|
| **ScreenTarget**（默认） | **DXGI 桌面复制 + 区域裁剪** | GDI（ScreenDC / mss） | 真正任意区域：浏览器、播放器、游戏、桌面都行；DXGI 不依赖目标是否响应 |
| **WindowTarget** | **WGC 窗口捕获** | PrintWindow | 能排除自身 HUD、能抓被遮挡窗口；需要目标窗口存在 |

> 关键区别：**WGC 只能"窗口"或"整个显示器"，不能直接抓任意子矩形**；所以"任意屏幕区域"必须走 DXGI/GDI，这是决策 8 的直接推论。

- **基准测速**：在**同一 target 类型**内比较可用后端（抓 90 帧，评分 = 有效帧率 / 首帧非黑 / 与参考后端一致性），选最高分；跨类型不比较。
- **回退**：连续 20 帧黑屏/超时 → 降级到该类型内的下一名并提示；设置里可锁定后端排障。
- **默认目标**：`ScreenTarget`（通用）。界面上给"选屏幕区域 / 选窗口"两个入口，窗口入口用于排障与遮挡场景。

**HUD 遮挡策略（G6）**

| 情况 | 策略 |
|---|---|
| 目标是 ScreenTarget 且 HUD 与区域相交 | ①自动把 HUD 移到不遮挡的角（优先）→ ②仍相交则录制期间隐藏 HUD → ③提示改用 WindowTarget |
| 目标是 WindowTarget | 无需处理（WGC/PrintWindow 不含其他窗口） |

**坐标模型（决策 4 + 8）**

1. `ScreenTarget` 存**屏幕物理像素矩形**（含显示器编号，支持多屏）；`WindowTarget` 存**客户端归一化矩形**（0..1）；
2. 运行时统一换算到"当前帧内的像素矩形"：
   - ScreenTarget + DXGI/GDI：直接用屏幕矩形（窗口移动不影响，因为是屏幕坐标）；
   - WindowTarget + WGC：按归一化比例裁窗口帧；
   - WindowTarget + DXGI/GDI：`ClientToScreen` 实时换算（窗口移动/缩放时重算）；
3. **标定期**把帧缩放到 1920×1080 跑一次 Hough（参数稳定）；**运行时**把键位坐标按比例映射回实际帧尺寸**直接采样，不做每帧 resize**；
4. 帧尺寸变化 / 显示器缩放变化 → 重新计算映射并提示（必要时重标定）；
5. **配置档（profile）** 保存：`{目标类型, 区域, 显示器, 乐器, 阈值, 后端, 16:9 基准}`，一键切换"游戏"与"浏览器视频"两套源（见 §8.4）。

### 6.2 视觉层参数

```python
# 标定期：1920x1080 参考帧
roi    = frame[int(h/3):, :]                       # 下 2/3（键区）
gray   = cv2.cvtColor(roi, cv2.COLOR_BGR2GRAY)
mask   = cv2.inRange(gray, 0, 239)                 # 高光挖空 → 琴键成"暗环"
circles= cv2.HoughCircles(mask, cv2.HOUGH_GRADIENT,
            dp=2.0, minDist=80, param1=20, param2=40,
            minRadius=40, maxRadius=53)
# 只把 Y 加回偏移 → 7 个一组 + 行/列均值吸附 → 按 NoteToKeyMap 顺序映射音名
```

> ⚠️ 坑：Hough 的 `param1/param2` 正确值与常见默认相反——运行时必须用 **`param1=20/param2=40`**（不是 40/20），以运行时配置为准。

**自动阈值标定（录制前，三步）**

1. 静默基线 2s → 每键 RGB 分布；
2. 逐键试按 → 按下分布；
3. 求解：选分离度最高的通道（`|Δmean|/std`）；`enter = release − 0.55Δ`、`exit = enter + 0.15Δ`；分离度不足的键标红提示；结果按 `(乐器, 分辨率, 皮肤)` 缓存进 `instruments.json`。

### 6.3 时间线

```python
class PressDetector:
    """施密特触发 + 最小按下 + 最小间隔（全部毫秒，帧率无关）"""
```

- 一期参数：`min_hold_ms=25`、`min_gap_ms=30`、`chord_window_ms=25`；
- 二期只把 `hold` 写入 `sustain_ms`，其余不变；
- 装配：`rest_i = onset_{i+1} − onset_i`，`sustain_i = hold_i`；
- 场景保护：一拍内 ≥ `key_count-5` 个键同时"按下" → 判过场，整段丢弃并 warning。

### 6.4 播放器（决策 1）

- **绝对时间表调度**：`while now < next_t: sleep(min(next_t-now, 5ms))`，抗漂移；
- 音频：`pygame.mixer` 预加载 21 个采样，按下即播，同音重触发先 `stop()`；
- 支持：播放/暂停/停止/定位/循环/变速（0.5–2.0x，时间是缩放，采样原速播放，**音高不变**）；
- 回调：每次切和弦给编辑器发 `(offset, length)` 做高亮 + 自动滚动；
- 解析有 Error 时禁用播放并定位到首个错误行。

### 6.5 编辑器（决策 1）

| 能力 | 实现 |
|---|---|
| 语法高亮 | 状态机扫描：注释、`@name/@instrument`、和弦字母、`.延音`、休止数字、非法字符标红 |
| 错误标记 | `Diagnostic(offset,length,level,msg)` → `setExtraSelections` 下划线 + 行号边栏 |
| 播放同步 | 选区高亮 + `ensureCursorVisible`（播放/定位时跟随滚动） |
| 统计 | 音符数 / 和弦数 / 时长 / 音密度 / 最长连续段 |
| 互转 | 打开 fengwu/domiso → 转 tick（带丢失告警） |
| 保存 | 另存 / 导出 tick / 导出 BGI JS / 复制 |

闭环：`识别结果 → 编辑器（光标停首个可疑处） → 空格播放 → 听到不对直接改 → 自动重解析 → 继续 → Ctrl+S`。

### 6.6 会话缓存

## 7. 输出格式

### 7.1 tick（默认）

```
/*
  @name <曲名>
  @instrument <乐器名>
*/
<CHORD>[.<sustain_ms>] <rest_ms> <CHORD>[.<sustain_ms>] <rest_ms> ...
```

- `CHORD` = 连续大写字母（同时按下）；`.sustain_ms` 仅当 `>=50` 输出；
- **`rest_ms` 必须输出且 ≥1**：tick 解析器会把"没有 Rest 分隔的连续 Chord"合并成一个和弦（格式本身的已知约束），生成端必须强制写 rest 才能兼容现有 tick 工具链；
- `rest_i = onset_{i+1} − onset_i`，`sustain_i = hold_i`（与 tick 播放器语义严格对应）。

```js
(async function () {
  try {
    const sheet = JSON.parse(file.readTextSync("sheet.json"));
    const t0 = Date.now() + 3000;                      // 倒计时，可配
    for (const e of sheet.events) {
      const target = t0 + e.t;
      while (Date.now() < target) await sleep(Math.min(target - Date.now(), 40));
      if (e.down) keyDown(e.key); else keyUp(e.key);
    }
  } catch (err) {
    log.error(`播放失败: ${err}`);
  } finally {
    for (const k of "ASDFGHJQWERTYUZXCVBNM") keyUp(k);  // 防卡键
  }
})();
```

| L3 Danger | danger 柔和底 + 红字（不实心） | `停止预览` / `停止录制` |

档位只换 `objectName`（映射在 `_refresh_action_emphasis()`），**`setEnabled` 时机一行不改**——可用性矩阵（初始/已标定/预览/录制/试听各态谁可用）与识别流程强绑定，改启用条件必须同步 03。

### 13.3 关键尺寸与响应式

- 窗口默认 **558×913** @(1393,50)、最小 **520×700**（三段各 28px 区块头，预览最小高 150 换回来的）；位置/尺寸 400ms 防抖落盘、closeEvent 立即落盘。
- 键位卡最小 64×64（三行：音名·键名 / 采样色 / Δ，等宽字体；Δ≥60% 转琥珀、按下整卡反色绿底）。
- 试听胶囊 `Media` 28×24 / 图标 18；编辑浮层宽 144 + 投影 + 指向箭头，点空白/Esc = 保存退出。
- 状态栏按宽度分档：≥620 全量（fps/源/单帧/帧数）、560~619（fps+帧数）、<560 只留 fps；徽标 + 单条消息区（info/warn/error 同位置）。

### 13.4 设计约束（改稿前必读）

1. **窄**：可用宽度 554~700px，优先竖向分组。
2. **暗**：贴在游戏旁边，整体亮度不能高；强调色只在"按下/播放"瞬间出现。
3. **等宽数值**：谱面/RGB/Δ/状态栏必须等宽，否则跳字。
4. **图标全部运行时自绘**（24 网格 + 4× 超采样，`icons.py`），不引位图/字体文件。
5. **不改控件语义**：按钮文案可改，启用条件改动必须同步 `docs/03`。

## 14. 截图方案技术总结（整合自原 05 · HDR 截图方案调研）

> 原 `05-HDR截图方案调研.md` 的浓缩版；完整根因推导、BGI/Maa 源码级对照与 BitBlt 逐项复核见 git 历史。

### 14.1 根因：HDR 下灰阶塌陷（不是黑屏）

HDR（或 Win11 24H2 ACM）下 DWM 把整个桌面合成为**线性 scRGB FP16**：`1.0 = 80 nits`，SDR 白点 = `SDRWhiteLevel_nits/80`（典型 2.5）。四条取帧路（BitBlt / `DuplicateOutput` / WGC-8bit / PrintWindow）都被系统**截断式**转 BGRA8——约 40% 线性亮度以上全部压到 255。我们的判据吃「键帽被压暗的差值」，信号直接消失；叠加基线在错误色值下学的 = 双错，所以是"完全不识别"。

### 14.2 BGI / MAA 的做法与结论

| 项目 | 做法 | 结论 |
|---|---|---|
| BGI | WGC 帧池申请 FP16 + 自写 shader（固定 `×0.25` 曝光 + 线性→sRGB）；另有注册表直接关游戏内 HDR | 固定白点是近似（官方自认"部分功能不可用"）；白点感知的 PR #3551/#3022 均未合并 |
| BGI BitBlt | **没有任何 HDR 代码**。"能用"是因为 `AutoDisableGenshinHdrEnabled`（默认 true）启动时把原神 HDR 关了 | 本机实测屏幕 DC BitBlt 16.7ms/帧，撑不住 60fps；其窗口 DC 经验不可搬到我们的屏幕区域截图 |
| MAA | 不做 HDR（PR #1105/#1300 均未合并），靠 6 种截图方法位掩码自动择优绕 | 换方法救不了 HDR（四条路吃同一个截断） |

### 14.3 正解与落地（M3e 已实现）

正解 = **`DuplicateOutput1` 取 FP16 + 按每屏 SDR 白电平归一 + 高光按最亮通道缩放保色相**（OBS/rustdesk/Sunshine 通行口径；BGI 的 ÷4 与 MAA 的 ACES 都不如它）。最终选现成轮子 **`j-hdrcapture`**（Rust 扩展，`hdrcapture`）：

- SDR 下**无损直通**（三路 A/B 与 GDI 平均绝对差 0.00）；`grab_region(1600×900)` 3.1ms（GPU 裁剪，别整屏读回）。
- 落地为 `capture/hdr_backend.py`（界面名 **j-HDR**，默认档）：区域必须完整落在单屏内；`AccessLost`/`DimensionsChanged` → 回退链 `hdr→dxgi→gdi`（回退必须说出来）；与 dxgi **互斥**（同一输出只允许一个 duplication 会话）。
- 打包必须 `hiddenimports += hdrcapture`（延迟导入）；剪 dxcam 子模块要 hiddenimports filter **和** `EXCLUDES` 两处同改。
- **切 HDR/后端后必须重学基线**（映射是单调的，同映射下学基线即可，但跨映射不行）。
- 已知限制：本机无 HDR 屏，HDR 效果待实机（`tools/hdr_probe/probe_hdr_ab.py`）；库 v0.1.0 太新，建议 vendored wheel；`adaptive=True` 会随内容压暗整屏，与差值判据冲突，**禁用**。

## 15. 键鼠模拟技术总结（整合自原 06 · BGI 与 MAA 键鼠控制方案调研）

> 原 `06-键鼠控制方案调研-BGI与MAA.md` 的浓缩版；源码级细节（接口签名、lParam 构造、方式矩阵全表）见 git 历史。

### 15.1 BGI（C#/.NET 8，单游戏专用）——抽象最干净

三层：`InputHub`（静态单例入口）→ `IInputBackend`（可整体切换：Win32/手柄/WebSdk）→ `IInputChannel`（**前台 SendInput + 后台 PostMessage 双通道**）。

- 前台：`Fischless.WindowsInput` 封装 SendInput，支持相对移动（视角）；扩展键自己判（左 Alt 不带扩展位、方向键带）。
- 后台：PostMessage，游戏不在前台时**每次操作前补发 `WM_ACTIVATE`**；lParam 手工构造（扫描码 + 扩展键第 24 位 + 抬起第 30/31 位）；仅支持键盘和鼠标左右键，无相对移动/滚轮。
- 音乐自动演奏（与我们最相关）：`KeyInputTransportBase` 模板——`HashSet` 按键去重 + `ReleaseAll` 兜底防键卡死；A–Z 直映射 VK。

### 15.2 MAA（C++ 动态库，通用框架）——输入方式全家桶

Win32 输入 10+ 种方式矩阵：Seize（SendInput 抢前台）/ SendMessage / PostMessage / **WithCursorPos**（短暂移光标再还原）/ **WithWindowPos**（短暂移窗口不抢鼠标）/ **Interception 驱动级注入** / 锚点触摸（WM_POINTER 全程不抢前台）等。两个黑科技：**MouseLockFollow**（窗口跟随鼠标 + RawInput 对冲硬件位移，注入 FPS 视角）、**BackgroundManagedKeys**（守护线程 5ms 巡检补键）。前台激活模板（`ForegroundUtils.h`）：`HWND_TOP` 提层 → `SetForegroundWindow` → `GetForegroundWindow` 复核 → 失败 TOPMOST↔NOTOPMOST 强提——TOPMOST 只保证最前不保证焦点，**以复核为准**。

### 15.3 YQRec 落地（M3g 已实现，`inputsim.py`）

- **结论：借鉴 BGI 的抽象用 Python ctypes 自实现（零第三方依赖），不引入 MAA 整个框架**；后台能力不够用（如目标程序检测真实光标）再上 MAA WithCursorPos 思路。
- 已实现：`left_click()`（模式 2）/ `press_space()` + `window_at()` + `is_own_window()` + `activate_window()`（模式 1），入口 `main_window._record_click_warmup()`，由 `instruments.json` 全局 int `record_click`（0/1/2）驱动，见 03 §5.1。
- 关键安全阀：激活复核不通过**坚决不发空格**（会落回本程序「录制」按钮误停录制）；命中本进程窗口不发；失败只提示不拦录制。
- 时机特权：用户刚点完「录制谱面」按钮 → 本进程是前台进程且收到最后输入事件 → 命中微软 `SetForegroundWindow` 放行条件，激活大概率一次成功。
- 待扩展：试听驱动游戏键（用 BGI 模板：去重 + ReleaseAll 兜底）；`settings.json` 可加 `input.backend`（**输入后端与截图后端是正交的两件事**）。
